关于姿态控制器的思考
首先Sunray的启动流程是
1. 启动sunray_uav_control -> sunray_mavros_exp.launch
2. 启动sunray_uav_control -> external_fusion.launch 并指定外部定位源
3. 启动sunray_uav_control -> sunray_control_node.launch
4. 启动sunray_uav_control -> terminal_control.launhc 调试使用
那么也就是说，前三步完成了从启动px4到通过程序进入offboard模式

**external_fusion**

external_fusion.launch文件通过指定外部定位源并进行订阅，然后转换坐标系(如果需要)，再将里程计数据转发到mavros/visvion_pose中，通过将外部里程计与px4的EKF2进行融合，然后发布目标点，期待PX4的响应。
而我们的姿态控制器期望实现高频的控制效果，因此我们希望绕过这一步，也就是实现 外部里程计数据 -> control节点 -> 姿态推力数据 -> PX4

那么这里存在的问题有: sunray_control_node节点对external_fusion节点中的数据具有紧耦合，也就是不启动external_fusion无法启动sunray_control_node，而如果不使用sunray_control_node就无法使用姿态控制器？

那么是否存在这样的可能，我们使用动捕的里程计，同时再姿态控制节点中直接订阅高频的外部里程计，然后向px4发布姿态-推力数据？
转换成具体的场景就是
```bash
# 启动mavros
roslaunch sunray_uav_control sunray_mavros_exp.launch
# 启动external_fusion 指定外部里程计为动捕
roslaunch sunray_uav_control external_fusion.launch external_source:=3
# 启动sunray_control_node,但是对该文件进行修改，设置控制模式进入位置-姿态推力模式
roslaunch sunray_uav_control sunray_control_node.launch 
# 启动修改后的terminal控制器
roslaunch sunray_uav_control terminial_viobot_control.launch
```

相比于原来的思路(重写external_fusion.launch或者是修改使其兼容viobot高频里程计)，这个思路显然会清晰一些，同时可以使用宏定义在测试代码和正常代码中进行切换。


**起飞逻辑**

起飞我们的想法是这样的，起飞的基本想法是不断的回顾历史里程计的数据，通过本次里程计和上一次里程计数据，来对当前要发布的数据进行修正，那么这里引入的问题是，我们是否直接通过姿态-推力控制器接口发送目标点为(0 0 1)就可以了，根据控制器内部的PID让他自己去进行控制？

关键：将(0 0 1)目标点分解为平滑的z(t)轨迹，通过姿态控制器的轨迹接口进行控制？这样会得到一个平滑的目标值

**如何评估控制器的性能**
控制器(如PID LQR MCP ...)的评估在于其鲁棒性，快速性，准确性
- 核心指标
  - 上升时间:响应从初始值达到目标值(90%)所需要的时间
  - 超调量：响应超过目标值的最大幅度
  - 调节时间：系统进入并保持在目标容差范围(对于无人机来说是+_5cm)内所需要的时间
  - 稳态误差：系统稳定后与目标值之间的稳定偏差
  - 控制带宽：控制器能跟踪信号的频率范围
- 评估场景
  - 阶跃响应：突然改变定值，观察系统恢复稳定的速度
  - 抗扰动能力：在运行中施加外力，观察系统能否快速回到轨迹
  - 给定一个复杂的动态轨迹，观察实际位置与期望位置的均方根误差 

**如何评估vio的性能**
- 核心指标
  - 绝对轨迹误差：对比vio的里程计和动捕的里程计
  - 相对位姿误差：对比vio的姿态和动捕的姿态
