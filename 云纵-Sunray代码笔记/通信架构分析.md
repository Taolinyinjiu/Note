我们注意到，`takeroff_hover_land.cpp`中接受到的无人机状态消息类型为`sunray_msgs::UAVState`，但是在最开始启动`roslaunch sunray_simulator sunray_sim_1uav.launch`时，我们的到的无人机状态，是通过mavros给出来的，仅仅只是进行了重映射，也就是说本质上`uav1/mavros/state`就是`mavros/state`,那么，是那个节点将`mavros/state`转换为了`sunray_msgs::UAVState`

转换后的无人机消息为 `/sunray/uav_state`
转换前的无人机消息为 `uav1/mavros/state`

找到与之相关联的节点就好了

通过运行`demo_takeoff_hover_land.sh`后对rqt的分析，我们不难发现,topic `/uav1/sunray/uav_state `类型即为`sunray_msgs/UAVState`,其发布者为`uav_control`,内部通过函数`uav_ctrl.show_ctrl_state`来实现将`mavros/sate`转换为`sunray/state`

通过对`UAVControl.cpp`文件的阅读，发现
```cpp
// 【订阅】PX4无人机综合状态 - 飞控 -> mavros -> external_fusion_node -> 本节点
px4_state_sub = nh.subscribe<sunray_msgs::PX4State>(uav_name + "/sunray/px4_state", 10, &UAVControl::px4_state_callback, this);
// 【发布】无人机状态（接收到vision_pose节点的无人机状态，加上无人机控制模式，重新发布出去）- 本节点 -> 其他控制&任务节点/地面站
uav_state_pub = nh.advertise<sunray_msgs::UAVState>(uav_name + "/sunray/uav_state", 1);
```
也就是说，`uav_control`是将`sunray_msgs::PX4State`转换为了`sunray_msgs::UAVState`，并且通过注释我们可以发现,节点`external_fusion_node`将`mavros/state`转换为了`sunray_msgs::PX4State`

关于external_fusion_node:
该节点订阅多个PX4的话题，并期望结合各种定位信息，比如Odom POSE Gazebo MoCap VioBOT GPS ，最终输出为一个自定义消息发布，也就是`sunray_msgs::UAVState`，这也就解释了为什么我们最开始就得到了`mavros/state`但还是绕了很大一个圈子最后的到了`sunray_msgs::UAVState`
